知识与决策 · 作者原文

为什么你的知识库撑不起关键决策？一号位缺的不是工具，是判断的连续性｜AI 知识库搭建（二）

Rebecca · AI Narrative Lab

上个月，我发布了第一篇 Obsidian 文章，讲我为什么要建立一套由自己掌握的第二大脑，以及我怎样用 IPO、总纲和 Agent 协作规则把它一点点搭起来。AI 越强，越需要一套全局「第二大脑」｜我的 Obsidian+Agents 搭建实践（一）

文章发出后，我收到最多的几个问题是：

这套知识库到底是怎样搭出来的？花了多长时间？门槛高不高？能不能有一套现成的 Skill，交给 AI，就让它帮我搭好？

后来，我给港科大 EMBA 的同学做了一次内部分享。现场不少同学本身就是理工科背景，也已经下载了 Obsidian，但迟迟没有开工。还有一些人，已经在飞书、网盘和自己的电脑里积累了大量文档，依然觉得自己没有一个真正的知识库。

他们有很多东西想存。行业资料、客户信息、项目进展、组织问题、管理判断、个人兴趣、临时冒出来的灵感，以及下次要和某个部门沟通的事。

这些内容在脑子里是立体的，彼此交叉；放到文件夹里，却似乎只能一层层排开。他们不知道怎样设计层级，哪些应该放在一起，哪些应该分开。越想一次设计完整，越难真正开始。

所以这一篇，想消除大家建知识库的阻力，把建知识库的第一步讲得更具体：怎样从复杂的工作中设计出第一版结构；哪些信息留给自己和 Agent，哪些进入客户和团队；又怎样借助 Agents，持续沉淀、调用和复用过去的经验。

一、先让 AI 还原：你每天到底在处理什么

有朋友问我怎样开始时，我曾经给过一个很实用的建议：

把我的第一篇文章和 IPO 那张图交给 AI，然后打开语音输入，把你平时在做什么、会看什么、对什么感兴趣、经常要产出什么，全部口喷给它。先不管结构，也不要边讲边替 AI 分类。

这个方法确实能帮很多人迈出第一步。但其实，这一步还可以做得更准确。

AI 要还原的，不只是一份工作清单，而是一号位完整的工作与信息全景：

目标与优先级：你长期想积累什么？当前哪些事最重要？
工作与判断：你反复在管什么？经常需要做哪几类决定？
信息与关注：你平时会读什么、收到什么？还会主动研究什么？
协作与边界：哪些信息只给自己，哪些可以给 Agent，哪些需要与客户或团队共用？
输出与反馈：这些信息最后要支持什么行动、产品或交付？哪些结果需要回来修正你原来的想法？

这里的目标尤其重要。一号位很少只有一个目标，增长、利润、创新、稳定、速度和风险控制，每一项都可能合理。AI 需要进一步知道：公司当前处于什么阶段，哪几件事优先，目标发生拉扯时怎样取舍，哪些边界不能突破，以及出现什么证据才算真正取得进展。

AI 可以继续追问你遗漏的部分，也可以先提出几套不同复杂度的结构，说明每套方案的取舍。

此时先不用急着决定工具。先确认这套知识库主要给谁使用、准备解决什么问题，再判断它更适合放在 Obsidian、飞书，还是其他载体里。

二、我的知识库里，有五类重要的文档

工作全景还原以后，下一步就该落到文件类型了。

我现在的知识库里，重要的大致是五类文档。它们不一定对应五个一级目录，但基本覆盖了我和 Agents 长期工作时最常调用的内容。

1. 长期知识

这里放 AI、投资、商业、品牌、脑科学、写作等领域中，经过加工、以后还会反复使用的知识。

一份报告、一段播客或一场 AI 对话，刚进入知识库时只是素材。经过理解、验证和连接，形成了可以复用的判断和方法，才会成为长期知识。

2. 项目总纲

每个重要项目都有一份唯一的项目总纲。它要说清楚：这个项目为什么存在，当前目标和边界是什么，哪份文档代表最新版本，已经进展到哪里，进入项目后应该先看什么。

项目材料可能很多，但项目总纲只能有一个。否则，新 Agent 找到几份都很完整的旧方案，很容易沿着已经失效的方向继续做下去。

3. 规则与操作手册

规则负责说明什么可以做、什么不能做、哪些动作必须先问、最后由谁裁决。操作手册负责说明一件具体工作怎样完成，例如一段 AI 对话怎样整理，素材进入哪里，完成后又要写回哪里。

这类文档让 Agent 不只读懂内容，也知道怎样在这套系统里行动。

4. 经验复盘

我会保留当时的判断、依据、假设和没有选择的方案。等结果出现以后，再单独写复盘，记录偏差为什么发生，哪些方法还成立，哪些规则需要修改。

例如：在投资研究里，如果形成了明确预测，我会先冻结当时的证据、条件和期限。结果出来以后新建复盘，而不是回头改写原来的判断。这样，Agent 才能分清哪些是事前判断，哪些是看到结果以后的解释。

5. 输出成果

公众号文章、演讲稿、方案、研究报告和客户交付，都属于输出成果。它们是某一轮工作的结果，也可能在发布、交付或使用后带回新的反馈。

这五类文档建立以后，还要解决一个更实际的问题：每次打开新的 Session，Agent 怎么知道自己应该先读哪一份？

三、为什么 Codex 每次进来都知道先读什么

最近又有朋友问我：为什么 Codex 进入这套知识库以后，知道自己该做什么、不该做什么？难道每开一个新 Session，都要重新告诉它先读总纲，再读项目文档吗？

在我现在使用的 Codex 环境里，不需要每次从头交代。系统会自动加载一份 AGENTS.md。我把跨项目长期不变的原则和知识库入口写在这里：只要任务涉及这套知识库，先读唯一的全局总纲。

全局总纲再根据任务，把 Agent 引向当前项目的项目总纲、具体操作手册，或者多 Agent 协作使用的 Workspace。

自动加载的 AGENTS.md
→ Obsidian 唯一全局总纲
→ 当前项目唯一的项目总纲
→ 按任务读取操作手册
→ 多轮或多 Agent 协作时进入 Workspace
→ 只有追溯原因时才读历史文档

AGENTS.md 负责开门，总纲负责带路，项目文档和操作手册负责告诉它这次具体怎样做。这样既不用每次把所有背景重新讲一遍，也不需要让 Agent 一上来就读完整个知识库。读得越多不一定越准确，过期方案和不相关的历史同样会制造噪声。

这不是所有 AI 工具天然具备的能力。这里说的是当前 Codex 的自动加载机制。换成其他 Agent，需要确认它是否支持类似的启动指令，或者为它另外建立固定入口。但背后的设计是通用的：先给 Agent 一个稳定入口，再让它按任务逐层读取，而不是每次把所有资料一次性塞进对话框。

四、Workspace 解决的，是多 Agents 怎样协作接棒

固定阅读顺序解决了 Agent 怎样进入系统。项目复杂起来以后，还要解决另一组问题：现在做到哪里了？这一轮由谁负责？上一轮留下了什么？下一棒从哪里开始？完成后写回哪里？

这套需求最早在 Vibe Coding 中变得很明显。同一个项目会经历产品定义、开发、测试、评审和修正，也会有多个 Agent 和多个 Session 先后参与。如果关键进展只留在聊天里，下一位 Agent 仍然要重新摸索。

我后来在 Obsidian 里建立了 Workspace。对外解释时，可以把它理解为一个多 Agents 协作运营台。它不存整个项目的所有资料，只保存继续协作所需的最小状态：

START HERE：这个 Workspace 管什么、先读什么、结果写回哪里；
看板：当前有哪些议题、处于什么阶段、下一棒是谁；
thread：这一轮的关键裁决、产物链接、未决问题和交接信息。

后来，这套结构首先用在了我的一个生产级的 vibe coding 项目上，规则稳定后，也用在了我的咨询服务项目 AI Narrative Lab 上。公司的定位、FDE 的边界、客户案例和对外 PPT 都经历过多轮研究与校准。新 Agent 进入时，先读项目总纲，再看当前看板和相关 thread，就能知道哪一份是母稿，哪一份是当前版本，哪些判断已经确认，哪些还需要我裁决。

完成以后，它再把结论、产物和下一棒写回 thread。正式成果进入 Outputs，客户资料回到客户目录，可以跨项目复用的方法再进入长期知识区。Workspace 只管理协作状态，不把所有文件再复制一遍。

五、一个人的认知后台，和团队的协作前台

我在一堂的「 AI 知识管理课程」里，听到过一个很有启发的区分：人和人的协作，继续用飞书（无广告）这类擅长共同编辑、讨论和形成共识的工具；以 AI 为主的上下文协作，本地 Markdown 文件用起来更直接、稳定。

我自己这几个月的实践，也越来越接近这个分工。

在 Obsidian 里，我会保留比较完整的开发上下文、投资研究、过程性判断、Agent 规则和项目历史。这些内容允许复杂，允许未完成，也可以保留很多只对我和 Agent 有用的技术细节。

在飞书里，我会把客户需要一起阅读、讨论、确认和长期使用的文档整理好。例如项目顶层文档、阶段进展、交付材料、团队 Know-how 知识库、项目管理 SOP、项目数据等。这里的语言、结构和权限，都要面向真正要使用它的人。

两边可以有部分重叠，但不需要 1:1 镜像。同一个项目，Obsidian 里可以保留「我和 Agent 到底怎样推到这个结论」；飞书里保留「客户和团队接下来需要理解、确认和执行什么」。

这也不是说「Obsidian 只给 AI，飞书只给人」。工具会继续变，AI 也可以通过工具访问飞书。选择的核心是判断放在哪里，当前这类信息主要给谁用，以及他们要在里面完成什么动作。

我还会保留一条很重要的治理边界：Agent 能用，不代表人可以不理解。

与目标、重要判断、权限和风险有关的内容，一号位仍然需要查看、理解和裁决。只有过程性的中间文件，才可以更多按 Agent 的阅读和处理习惯来设计。

六、这套结构带来的，是三种连续性

真正持续使用知识库以后，我感受更深的是三种「连续性」。

第一，判断不再只活在当下

一次决定的目标、依据、假设和放弃的选项被留下来。下次遇到类似问题时，可以继续上一次的讨论，而不是重新凭印象讲一遍。

第二，协作可以穿过不同 Agents 和 Sessions

新的 Agent 不再只拿到一句任务。它可以知道这件事为什么做，过去发生过什么，现在以哪份文档为准，自己这一棒应该交付什么。

第三，经验可以根据真实结果持续优化

项目结果、客户反馈和真实数据回到系统，过去的方法和判断才有机会被改写。对一个组织来说，这也意味着它能够逐渐积累更连续的历史、更明确的假设和可以回看的证据。

它不会让一个组织自动得到正确预测，但能让整个组织的下一次分析站在更稳定、更高水准的基础上，更快对齐、持续迭代进步。

七、一号位怎样搭出 1.0 版

第一版不用搬完全部历史资料，也不用预先设计几十个模板。可以先完成下面几步：

一号位多轮口述
→ AI 还原工作与信息全景
→ 确认目标、优先级和边界
→ 生成两三套候选结构
→ 用三到五份真实材料试放
→ 选择一个真实项目跑起来

测试材料可以包括一份行业报告、一段 AI 对话、一个正在推进的项目、一个尚未想清楚的经营判断，以及一份需要与他人共用的文档。看看它们应该从哪里进入，处理后去哪里，以后还能不能找回来。

先建立五类核心文档的最小版本。等一个项目真的出现多轮、多 Agent 接棒，再增加 Workspace。能够支撑一个真实项目连续运行，就是知识库 1.0。

结尾

我自己的系统建在 Obsidian 上，因为我需要多个 Agent 直接使用同一批本地文件，也需要长期保留开发、投资、内容和客户项目中尚未完成的判断。

最近，我也开始帮助一位企业创始人启动她的一号位知识库。

工具可以不同，核心都是把一号位的目标、判断、规则、知识和经验，从会议、聊天和个人记忆中逐步留下来。下一次遇到类似问题时，人、Agent 甚至团队都不必重新从零开始。需要强调的是，我在给企业做诊断时，发现刚接触 AI 的人，总习惯性想把「判断」和「决策」交给 AI，自己只是描述过程，这是最忌讳的。

如果你也积累了大量资料、经验，却一直没有形成自己的系统，但很期待借助 AI 形成属于自己和组织的一套第二大脑的飞跃，可以发我关键词：「一号位知识库」。
